## 2. 현재 어디까지 구성되었는가

1. 구성됨: TypeScript/React/SQLite/MCP Apps. `src/contracts`는 계약, `domain`은 날짜/연속 기록/목표 계산, `application`은 유스케이스, `infrastructure`는 저장, `mcp`는 도구, `ui/src`는 임베디드 화면이다.
2. 구현됨: 프로필·활동 CRUD·버전 충돌/중복 방지·사진/분석/체크/목표·백업/복구·리뷰 컨텍스트·로컬 알림 설정. 사진과 건강 자료는 로컬 DB이며 Git 제외.
3. 이번 UX: 왼쪽 1열 체크/오른쪽 동시 지표, 하단 날짜 이미지북, 목표 ✓ 비율 잔디, 불필요한 오버레이/호스트 설명 제거. 번호별 기준은 UX.md에 둔다.
4. 검증: 이번 변경 후 타입 검사/빌드/18개 도메인·저장 시험 및 실제 MCP/백업/probe 재통과. 실제 React/합성 SQLite 브라우저에서 PC 배치·0~4 잔디·사진 업로드/탐색·재조회·360px dark 넘침 검증 및 합성 화면 육안 확인. 호스트/AI bridge는 모사한다. 상세 근거는 VALIDATION의 HAN-8 항목에 둔다.
5. 실제 수용 미완료: 최신 생산 UI·새 채팅·실제 AI 인식/목표 초안·카메라/폴더 권한·OS 알림·클라우드 예약/모바일 푸시. harness의 AI/호스트는 모사이며 실제 인식 품질의 근거가 아니다.
6. 전달: 사용자 명시 요청으로 `codex/mvp`의 최초 커밋 `437afe0`을 GitHub에 푸시하고 원격 SHA 일치 확인. 후속 변경의 전달 여부는 CHANGELOG/Linear 체크포인트에 따로 기록한다.
7. 미지원/후속: 앱 종료 후 사진함 자동 접근·모바일 백그라운드, 자동 사이드바 고정/순서, 임의 목표 편집/날짜별 목표 버전, 복수 사진 식사 통합. 구현되지 않은 기능을 UI에서 약속하지 않는다.

## 3. 상태 전이에 따라 수행할 단계

1. 아이디어 구상 → 구체화: 문제·사용자·성공 시나리오를 정하고 착수 요청을 확인한다. 원문/미결정/제안을 구분한다.
2. 구체화 → MVP: 파일 구조·아키텍처·스택, 모호한 요구 질문/답, 추천 개선안/합의, 기능별 상태/데이터 정책/수용 기준, 스텝별 구현 순서와 MVP 구현 경계를 확정한다. 구현 승인 후 가장 작은 끝까지 동작하는 흐름부터 만든다.
3. 현재 MVP: HAN-8 UX를 구현·관련 시험으로 검증하고 HAN-5/6/7의 실제 대상 환경 수용 차이를 닫는다. 구현, mock, API, 실제 화면 확인을 각각 기록한다.
4. MVP → 제품화: 핵심 흐름의 실제 수용 근거와 제품화 범위/착수 승인을 확인한다. 작업을 신뢰성, 데이터 마이그레이션·복원·삭제, 권한/보안, 설치/업데이트, 성능/용량, 접근성/지원 환경, 회귀 시험, 운영/복구로 나눠 담당·수용 기준·우선순위·근거를 적고 승인된 작업을 수행한다.
5. 제품화 → 출시/Analytics: 차단 결함 해결·출시 후보 품질 증거·비차단 항목의 합의된 이월, 배포/지원/측정 범위와 착수 승인을 확인한다. 버전·변경 기록·설치·핵심 smoke 시험·롤백/복구·최소 지표를 준비한다. 새 원격 telemetry/비용/전송은 승인 범위를 확인한다.
6. 출시/Analytics → Completed: 승인된 실제 배포/설치·운영/측정의 합의 결과 및 종료 기준과 종료 요청/승인을 확인한다. Canceled는 명시적 취소에만 쓴다.

## 4. Linear와 코드 문서의 갱신 규칙

생성 전 중복 조회 → 수정 직전 최신 상태/동시 변경 확인 → 변경 → 재조회. 요구 ID ↔ 이슈 ↔ 코드 경로 ↔ 검증 근거를 연결한다. 요구 변경은 UX.md, 변경 이력은 CHANGELOG, 현재 체크포인트는 이 파일과 Linear, 검증 상세는 VALIDATION에 둔다.
전이 기록에는 이전→다음, 대상/일시, 승인 근거, 테스트 환경/버전, 차단/미검증/이월과 담당·다음 행동을 적는다. 프로젝트 상태와 개별 이슈 상태를 별도로 관리한다. 기존 승인을 재질문하지 않으며 문서 작성·빌드·푸시 성공을 실제 제품화/출시 완료로 간주하지 않는다.

## 제품화 필수 작업 4축 · 2026-10-11 사용자 승인 범위
1. **사용자 경험**: 사용자가 실제로 다듬는 요구를 번호화하고 UI·상태·접근성·반응형 수용 기준으로 연결한다. 에이전트는 승인된 개선과 회귀 검증을 수행하고 사용자는 실제 사용감을 평가한다.
2. **권한**: 개발자의 공식 UI/기능 수정·배포 권한과 이용자의 자기 기록·작업·프로필·알림 관리 범위를 구분한다. 로컬/서버/클라우드 여부와 무관하게 데이터 소유·읽기/쓰기/삭제·기기/파일 접근·AI 전송 권한을 명시한다. UI 숨김을 권한 검증으로 보지 않는다. 현재 Fitlog는 단일 로컬 사용자이며 로그인/RBAC는 미구현이다. 로컬 컴퓨터 소유자의 파일 수정을 막는다고 주장하지 않는다. 다중 사용자/공유가 적용되기 전 도구·데이터 계층의 소유권 검증, 거부/철회·타인 ID 접근 음성 테스트가 필요하다. 권한 설계/구현은 후속 범위이며 새 인증/클라우드 도입을 자동 승인하지 않는다.
3. **도움말**: 작업을 방해하지 않는 화면 도움말과 채팅/MCP 사용법을 제공한다. 공통 원본에서 지원·호스트 의존·예정 기능을 구분하고 오류·제한·권한도 안내한다. 설명의 정확성·발견성·키보드 조작을 검증한다.
4. **테스트 코드와 시나리오**: 요구 ID → 사전 조건/입력 → 기대 도구 호출·저장 상태·출력·화면 → 자동 테스트 경로 → 실행 근거/미검증을 연결한다. 단위·DB·실제 MCP 통합·앱 UI·실제 AI 채팅·실제 대상 호스트를 구분한다. PC/모바일, 상태 전이/최신화, 첨부·인식·저장·재조회, 권한 거부, 오류/충돌/재시도/복구를 포함한다. 미지원 흐름은 실패를 감추지 말고 명확한 제한 안내를 수용 기준으로 둔다.

전이 운영: 구체화에서 위 4축의 범위·담당·수용 기준을 정하고, MVP에서 핵심 코드/테스트/지원 한계를 만든다. 제품화에서는 실패 시나리오·실제 통합·회귀 코드와 근거를 보강한다. 출시/Analytics 전에는 핵심 시나리오 실제 대상 환경 통과와 권한/데이터 유실/핵심 흐름 차단 해소를 확인한다. 각 축에 적용 여부·담당·환경/버전·통과/실패/미검증·근거·이월 결정을 기록한다. 문서 작성·에뮬레이터 통과만으로 Linear 상태를 이동하지 않는다.
